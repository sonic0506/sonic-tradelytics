# 01. 실시간 데이터 받기: 웹소켓 vs REST 폴링 vs SSE

> 상태: 초안 · 담당: @소닉 · 최종 수정: 2026-10-27 · 상위: [기술 선택 학습 자료](./README.md)
> 관련 결정: [ADR-0007](../architecture/adr/0007-single-market-collector.md) · [Q-001](../project/open-questions.md#q-001) · [토스 연동 웹소켓](../integrations/toss-securities-api.md#웹소켓)

## 한 줄 요약

시세와 내 주문 체결은 **웹소켓 연결 1개**로 받고, 웹소켓에 없는 데이터(분봉, 순위)만 REST로 가끔 조회해요.

## 먼저 알아둘 용어

| 용어 | 무엇인가 |
| --- | --- |
| REST 폴링 | 클라이언트가 "새 소식 있어?"라고 HTTP 요청을 주기적으로 반복하는 방식. 요청할 때만 데이터가 와요 |
| 롱 폴링 | 요청을 보내면 서버가 새 데이터가 생길 때까지 응답을 붙잡고 있다가 보내는 방식. 받으면 바로 다시 요청 |
| 웹소켓 (WebSocket) | HTTP로 시작한 연결을 계속 열어 두고, 서버와 클라이언트가 **양방향**으로 메시지를 보내는 프로토콜 |
| SSE (Server-Sent Events) | HTTP 응답을 끊지 않고 서버가 **한 방향**(서버 → 클라이언트)으로 이벤트를 계속 흘려보내는 방식. 브라우저 `EventSource`가 재연결을 자동으로 해줘요 |
| 웹훅 (Webhook) | 일이 생기면 **서버가 내 서버의 URL로** HTTP 요청을 보내주는 방식. 내 서버가 외부에서 접근 가능해야 해요 |

## 우리가 풀어야 하는 문제

- 장중에 여러 종목의 체결가·호가를 몇 초 이내로 알아야 해요 (스캘핑·데이 트레이딩)
- 내 주문이 체결됐는지 바로 알아야 손절 조건주문을 걸 수 있어요
- 토스 REST 한도: 시세 `MARKET_DATA` 초당 15회
- 토스 웹소켓 한도: 계정당 연결 2개, 연결당 구독 100건, 시세 프레임은 유실 가능(LOSSY)

## 선택지 비교

| 방식 | 지연 | 호출 한도 부담 | 구현 난이도 | 우리 상황 |
| --- | --- | --- | --- | --- |
| REST 폴링 | 폴링 주기만큼 늦음 | 종목 수 × 주기만큼 호출. 20종목을 1초마다 보면 초당 20회로 한도 초과 | 쉬움 | 감시 종목 수와 주기가 크게 제한돼요 |
| 롱 폴링 | 짧음 | 서버가 지원해야 함 | 보통 | 토스가 제공하지 않아요 |
| **웹소켓** | 거의 즉시 | 구독 한 번이면 계속 받음 | 어려움 (재연결, 유실 대응) | 토스가 시세·주문 이벤트를 웹소켓으로 제공해요 |
| SSE | 거의 즉시 | 구독 한 번 | 보통 | 토스가 제공하지 않아요. 우리 **웹 화면** 쪽에서는 후보예요 ([12](./12-frontend.md)) |
| 웹훅 | 거의 즉시 | 없음 | 보통 | 토스 문서에 없어요. 있더라도 서버를 외부에 열어야 해서 [ADR-0006](../architecture/adr/0006-network-level-access-control.md)과 맞지 않아요 |

**연결을 누가 여나**도 따로 골라야 했어요.

| 방식 | 장점 | 단점 |
| --- | --- | --- |
| 봇마다 웹소켓 연결 | 봇끼리 독립적 | 계정당 연결 2개라 봇 3개부터 불가능 |
| **공용 수집기 1개 (MarketCollector)** | 같은 종목은 한 번만 구독, 한도 관리가 한 곳 | 수집기가 죽으면 모든 봇이 시세를 못 받음 → 신선도 검사로 멈춤 |

## 선택과 이유

- 웹소켓: 지연과 호출 한도 두 가지를 동시에 해결하는 유일한 방법이에요
- 공용 수집기 1개 + 메모리 스냅샷: 봇은 API를 직접 부르지 않고 스냅샷만 읽어요. 나머지 연결 1개는 예비로 남겨요
- REST는 보조로만: 웹소켓에 없는 분봉·순위·지수, 그리고 유실 보정과 재연결 후 재동기화

## 감수한 것

- **재연결 코드가 필요해요.** 하트비트(`PING` 60초), 끊김 감지, 재연결, 구독 재선언, 주문 상태 재조회까지 직접 만들어야 해요. REST 폴링에는 없는 복잡도예요
- **유실을 감지할 수 없어요.** 시세에 순번(sequence)이 없어서, 마지막 수신 시각으로 "오래됐다"만 판단하고 분봉 REST 값으로 보정해요
- **끊긴 동안의 주문 이벤트는 다시 오지 않아요.** 그래서 이벤트(빠름)와 REST 재조회(정확)를 같이 써요

## 다시 검토할 때

- 감시 종목이 50개(체결+호가 100건)를 넘으면: 예비 연결을 쓰거나 우선순위 낮은 종목을 REST로 내려요
- 토스가 시세 순번이나 재전송을 지원하면: 유실 보정 로직을 줄일 수 있어요

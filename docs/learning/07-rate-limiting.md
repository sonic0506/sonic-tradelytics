# 07. 호출 한도 제어: 토큰 버킷, 그리고 "기다리기 vs 건너뛰기"

> 상태: 초안 · 담당: @소닉 · 최종 수정: 2026-10-27 · 상위: [기술 선택 학습 자료](./README.md)
> 관련 결정: [ADR-0007](../architecture/adr/0007-single-market-collector.md) · [토스 연동 호출 한도](../integrations/toss-securities-api.md#호출-한도-rest-클라이언트--그룹-초당) · NFR-03 · R-005

## 한 줄 요약

토스 API 그룹마다 **토큰 버킷**을 하나씩 두고, 한도가 모자라면 **기다리지 않고 그 판단을 건너뛰어** 기록해요. 숫자는 상수가 아니라 응답 헤더를 따라요.

## 먼저 알아둘 용어

| 용어 | 무엇인가 |
| --- | --- |
| 레이트 리미팅 | 일정 시간에 보낼 수 있는 요청 수를 제한하는 것 |
| 고정 창 (fixed window) | "매 초 0~999ms 동안 15회"처럼 구간마다 횟수를 셈. 구간 경계에서 순간적으로 두 배가 몰릴 수 있어요 |
| 슬라이딩 창 | "지금부터 직전 1초 동안 15회"처럼 움직이는 구간으로 셈. 경계 문제가 적어요 |
| 토큰 버킷 | 버킷에 토큰이 일정 속도로 채워지고, 요청마다 하나씩 꺼내 써요. 토큰이 없으면 요청 불가. 순간적인 몰림(버스트)을 버킷 크기만큼 허용 |
| 리키 버킷 | 요청을 큐에 넣고 일정 속도로만 흘려보냄. 출력이 일정해요 |
| 429 / `Retry-After` | "너무 많이 보냈다"는 HTTP 응답과, 몇 초 뒤 다시 하라는 헤더 |
| 지수 백오프 + jitter | 재시도 간격을 1초, 2초, 4초…로 늘리고 무작위 값을 섞어 재시도가 한꺼번에 몰리지 않게 함 |
| `bottleneck`, `p-limit` | Node.js에서 호출 속도·동시 실행 수를 제한하는 라이브러리 |

## 우리가 풀어야 하는 문제

- 토스 한도는 **그룹별·초당**이에요 (예: `MARKET_DATA` 15, `ORDER` 10, 09:00~09:10 `ORDER_INFO` 3)
- 한도는 **사전 공지 없이 바뀔 수 있어요**
- 짧은 시간 대량 주문은 **어뷰징으로 매매 제한**을 받아요
- 판단은 그 시점 시세로 해야 의미가 있어요. 늦게 낸 주문은 다른 가격에 체결돼요

## 선택지 비교

**알고리즘**

| 방식 | 장점 | 단점 | 우리 상황 |
| --- | --- | --- | --- |
| 고정 창 | 구현이 가장 쉬움 | 경계에서 한도의 두 배가 나갈 수 있음 | 서버가 거부할 위험 |
| 슬라이딩 창 | 정확 | 요청 시각 기록이 필요 | 가능 |
| **토큰 버킷** | 평균 속도 + 짧은 버스트 허용, 구현이 간단 | 버킷 크기를 잘 정해야 함 | 채택. 그룹별 버킷 |

**한도가 모자랄 때**

| 방식 | 장점 | 단점 | 우리 상황 |
| --- | --- | --- | --- |
| 큐에 넣고 기다리기 | 요청을 잃지 않음 | 시세가 지나간 뒤 주문이 나감, 대기가 쌓이면 폭주 | 매매 판단에는 위험 |
| **건너뛰고 기록** | 오래된 판단으로 주문하지 않음 | 기회를 놓침 | 안전 우선 원칙(NFR-01)과 맞음 |
| 일단 보내고 429 받으면 재시도 | 구현 쉬움 | 한도 초과가 반복되면 제재 위험 | 보조 수단으로만 |

## 선택과 이유

- TossClient 한 곳에서 그룹별 토큰 버킷으로 속도를 제한해요 (호출을 한 프로세스에 모은 이유이기도 해요, [03](./03-process-structure.md))
- 한도 숫자는 `X-RateLimit-*` 헤더로 갱신하고, 429면 `Retry-After`를 따르며 백오프해요
- 매매 판단에 필요한 호출은 **기다리지 않아요.** 한도가 없으면 "건너뛴 판단"으로 남겨요
- 배치처럼 늦어도 되는 호출은 기다려도 돼요

## 감수한 것

- 장 초반처럼 호출이 몰리는 시간에는 판단 기회를 놓칠 수 있어요
- 시세를 웹소켓으로 받는 이유 중 하나가 이 한도예요 ([01](./01-realtime-data.md))

## 다시 검토할 때

- 건너뛴 판단 중 "한도 부족" 사유가 많으면: 호출 패턴(스냅샷 주기, 조회 종목 수)을 줄이거나 우선순위 큐 도입

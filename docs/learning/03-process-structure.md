# 03. 프로세스 구조: 단일 프로세스 vs api·engine 분리 vs 마이크로서비스

> 상태: 초안 · 담당: @소닉 · 최종 수정: 2026-10-27 · 상위: [기술 선택 학습 자료](./README.md)
> 관련 결정: [ADR-0002](../architecture/adr/0002-split-api-and-engine.md) · [시스템 개요](../architecture/overview.md)

## 한 줄 요약

코드베이스는 하나(`apps/server`), 실행 프로세스는 둘이에요. 매매를 하는 **engine**과 화면을 위한 **api**로 나누고, 둘은 Postgres로만 소통해요.

## 먼저 알아둘 용어

| 용어 | 무엇인가 |
| --- | --- |
| 프로세스 | 운영체제에서 따로 실행되는 프로그램 하나. 하나가 죽어도 다른 프로세스는 계속 돌아요 |
| 모놀리스 | 모든 기능을 하나의 프로그램으로 배포하는 구조 |
| 모듈러 모놀리스 | 코드는 하나지만 내부를 모듈로 나누고, 필요하면 진입점을 여러 개 두는 구조. 우리가 이 방식이에요 |
| 마이크로서비스 | 기능마다 별도 서비스·배포·DB를 두고 네트워크로 통신하는 구조 |
| 진입점 (entrypoint) | 프로그램이 시작하는 파일. `main.ts`를 둘 두면 같은 코드로 다른 프로세스를 띄울 수 있어요 |
| 장애 격리 | 한 부분의 문제가 다른 부분으로 번지지 않게 하는 것 |

## 우리가 풀어야 하는 문제

- 매매 루프는 장중에 **멈추면 안 돼요.** 웹 배포, 무거운 조회, 화면 버그가 매매를 끊으면 안 돼요
- 토스 토큰은 **클라이언트당 1개**, 웹소켓은 **계정당 2개**예요. 여러 프로세스가 각자 토큰을 발급하면 서로 끊어요
- 1인 개발·운영이에요

## 선택지 비교

| 방식 | 장애 격리 | 토큰·연결 관리 | 운영 부담 | 우리 상황 |
| --- | --- | --- | --- | --- |
| 단일 프로세스 | 없음. 웹 오류·배포가 매매를 끊음 | 쉬움 (한 곳) | 가장 적음 | 장중 웹 배포를 못 해요 |
| **api·engine 분리 (코드 하나)** | 웹과 매매가 서로 영향 없음 | engine 한 곳에만 둠 | 프로세스 2개, 배포 1개 | 요구사항을 만족하면서 단순 |
| 마이크로서비스 (시세·주문·리스크·화면 각각) | 가장 세밀 | 서비스 간 조율이 어려움 | 서비스·배포·통신이 여러 개 | 1인 운영에 비해 과해요 |

## 선택과 이유

- **engine**: BotRunner, Scheduler, TossClient, Notifier. 토스 API를 부르고 토큰을 발급하는 **유일한** 프로세스. 동시에 하나만 떠요
- **api**: 화면용 조회, 봇 설정 저장, 명령 접수. 토스 API를 직접 부르지 않아요
- 소통은 Postgres로만 ([02](./02-messaging-and-queues.md)). 코드가 하나라 타입·도메인 로직을 공유해요

## 감수한 것

- 화면의 잔고는 engine이 DB에 쓴 값이라 **몇 초 늦을 수 있어요**
- engine 중복 실행을 막는 잠금이 필요해요 (Postgres 어드바이저리 락 등, [05](./05-database-and-orm.md))
- engine 안에서 봇 하나의 예외가 프로세스 전체를 죽이지 않게 **봇 단위 격리**를 코드로 만들어야 해요

## 다시 검토할 때

- 백테스트처럼 무거운 계산이 생기면: 별도 워커 프로세스(세 번째 진입점)를 추가
- 여러 사람이 쓰는 서비스가 되면: 사용자별 토큰·연결 관리 때문에 구조를 다시 봐요

# 08. 주문 안전 설계: 멱등 키, 기록 먼저, 증권사 조건주문 손절

> 상태: 초안 · 담당: @소닉 · 최종 수정: 2026-10-27 · 상위: [기술 선택 학습 자료](./README.md)
> 관련 결정: [ADR-0003](../architecture/adr/0003-record-decision-before-order.md) · [리스크 관리 §5, 7, 7-1](../policy/risk-management.md#5-주문-폭주-방지) · R-001, R-006

## 한 줄 요약

판단을 DB에 먼저 저장하고 그 id를 **주문의 멱등 키**(`clientOrderId`)로 써요. 손절은 서버가 아니라 **증권사 조건주문**에 맡겨, 서버가 죽어도 작동하게 해요.

## 먼저 알아둘 용어

| 용어 | 무엇인가 |
| --- | --- |
| 멱등성 | 같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같은 성질 |
| 멱등 키 | 요청마다 붙이는 고유 id. 서버가 이 id를 기억해 중복을 막아요. 토스는 `clientOrderId`, 유효 10분 |
| 정확히 한 번 (exactly-once) | 네트워크에서는 보장하기 어려워요. 보통 "최소 한 번 보내기 + 멱등 키로 중복 제거"로 만들어요 |
| 트랜잭셔널 아웃박스 | DB에 "보낼 메시지"를 먼저 저장하고, 별도 과정이 그것을 외부로 보내는 패턴. 기록과 전송의 불일치를 막아요 |
| 조건주문 | 가격 조건이 맞으면 증권사가 대신 주문을 내는 기능. 내 서버가 꺼져 있어도 작동 |
| 정답 출처 | 기록이 어긋나면 어느 쪽을 믿을지. 우리는 증권사 주문 조회 결과 |

## 우리가 풀어야 하는 문제

- 네트워크 오류로 **재시도할 때 중복 주문**이 나면 안 돼요
- **모든 봇 주문에 근거 기록**이 있어야 해요 (G1, 100%)
- 서버·네트워크가 죽어도 **보유 포지션이 손절 없이 방치되면** 안 돼요 (R-006)

## 선택지 비교

**주문과 기록의 순서**

| 방식 | 장점 | 단점 | 우리 상황 |
| --- | --- | --- | --- |
| 주문 후 기록 | 주문이 빠름 | 주문은 됐는데 기록 실패 → 근거 없는 주문 | G1 위반 |
| **기록 먼저, 그 id를 멱등 키로** | 근거 없는 주문이 구조적으로 불가능, 재시도 안전 | 주문 전 DB 쓰기 1회만큼 지연 | 채택 |
| 별도 UUID + 매핑 테이블 | 판단과 주문 id 분리 | 키가 둘이라 추적 복잡 | 이득 없음 |
| 아웃박스 + 별도 전송 프로세스 | 기록·전송 완전 분리 | 프로세스·지연 추가 | 우리는 기록 행 자체가 아웃박스 역할을 해요 |

**손절 방식**

| 방식 | 장점 | 단점 | 우리 상황 |
| --- | --- | --- | --- |
| 서버가 시세를 보고 매도 | 조건을 자유롭게 | 서버가 죽으면 손절도 멈춤 | 단독으로는 위험 |
| **증권사 조건주문 (`SINGLE`+시장가 매도)** | 서버가 죽어도 작동 | 국내는 KRX 정규장에서만 발동, 누구의 주식인지 모르고 수량만큼 팖 | 채택. 매매를 정규장으로 한정 (POL-RISK-15) |
| `OCO` (익절·손절 묶음) | 하나 발동 시 다른 것 자동 취소 | 지정가만, 종목당 1개 | 여러 봇이 같은 종목을 다루면 막혀요 |

## 선택과 이유

- 판단 id(UUID 36자)를 그대로 `clientOrderId`로 써서 키가 하나예요. 재시도는 같은 키로만, 10분이 지나면 먼저 주문 조회로 확인해요
- 손절은 진입 체결 직후 조건주문으로 걸고, 봇이 팔기 전에는 **먼저 조건주문을 취소하고 확인한 뒤** 팔아요 (POL-RISK-14)

## 감수한 것

- 주문 직전 DB 쓰기만큼 지연이 늘어요. 스캘핑에서 문제가 되면 측정 후 다시 봐요
- 조건주문과 봇 매도의 순서를 지키는 코드가 복잡해요 (취소 확인, 이미 발동한 경우 처리)
- 정규장 밖에서는 손절 안전망이 없어서 그 시간에는 매매하지 않아요

## 다시 검토할 때

- 토스가 정규장 밖 조건주문 발동을 지원하면: 매매 시간 제한(POL-RISK-15)을 다시 봐요

### Q-021

**앱 로그인이 없는데 서버 하네스의 전역 인증 가드를 어떻게 맞추나?**
[ADR-0006](../architecture/adr/0006-network-level-access-control.md)은 Tailscale 안에서만 접근하고 앱 로그인을 만들지 않기로 했어요. 그런데 서버 하네스는 모든 API에 JWT 로그인을 요구하고(전역 `JwtAuthGuard`), e2e가 `@Public()`이 아닌 모든 경로의 401을 확인해요([하네스 5절](../../apps/server/.sonic-harness-be/harness.md)). 이 API는 실제 주문을 일으키므로 네트워크가 뚫렸을 때 한 겹이 더 있는 편이 안전해요 ([API 명세](../architecture/api.md#공통-규칙)).

> **결정 (2026-10-28)**: A. 로그인 API를 만들지 않고, 서버 비밀 키로 서명한 만료 긴 JWT 하나를 web 서버 쪽 환경 변수에만 둬요. 브라우저는 web 서버를 거쳐 api를 불러요 → [API 명세 인증](../architecture/api.md#인증)

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| **A. 로그인 API 없이, 서버 비밀 키로 서명한 만료 긴 JWT 하나를 web 서버 쪽 환경 변수에만 둬요. 브라우저는 web 서버(Next.js)를 거쳐 api를 불러요** | 하네스 가드·e2e 그대로. 네트워크가 뚫려도 토큰 없이는 못 불러요. 브라우저에 토큰이 없어요 | web이 api를 대신 부르는 구조가 필요해요. 토큰을 바꿀 때 web 재배포가 필요해요 |
| B. 모든 controller에 `@Public()` | 가장 단순 | 가드가 없는 것과 같아요. 네트워크 하나만 믿어요 |
| C. 하네스 방식대로 로그인(비밀번호) 구현 | 하네스 기본 흐름 그대로 | ADR-0006 결정과 어긋나고 만들 코드가 늘어요. 휴대폰에서 킬 스위치를 누르기 전에 로그인이 필요할 수 있어요 |

### Q-020

**규칙 평가 순수 함수(`evaluate(type, params, snapshot)`)를 어느 파일에 두나?**
서버 하네스는 feature 안 파일 이름을 접미사로 제한해요(`*.service.ts`, `*.constants.ts`, `*.types.ts` 등, [하네스 1절](../../apps/server/.sonic-harness-be/harness.md)). 순수 함수용 레이어가 없어서, 그대로 두면 Nest 서비스 안에 넣어야 해요. 백테스트·PaperBroker가 Nest 없이 같은 함수를 부르려면 서비스 밖이 편해요 ([ADR-0005](../architecture/adr/0005-in-house-paper-broker.md), [엔진 설계](../architecture/engine.md#모듈-배치)).

> **결정 (2026-10-28)**: A. 하네스에 `*.rule.ts` 레이어를 추가해요. rule 파일은 같은 feature의 `constants`·`types`와 `common`만 가져오고, 같은 feature의 service가 rule을 불러요. 하네스 원본에도 올려요 → [엔진 설계 모듈 배치](../architecture/engine.md#모듈-배치)
>
> **구현 (2026-10-29)**: 프로젝트 하네스에 추가했어요. lint가 rule 파일의 Nest·TypeORM·`node:` import와 `Date.now()`·인자 없는 `new Date()`·`Math.random()`을 막아요. 하네스 원본 반영은 남았어요

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| **A. 하네스에 `*.rule.ts` 레이어 추가 (import는 같은 feature의 constants·types, common만)** | 순수 함수가 Nest·DB를 못 가져오게 lint가 막아요 | 하네스 규칙 변경이라 원본 하네스에도 반영해야 해요 |
| B. `strategy.service.ts` 안에 두고 메서드로 노출 | 하네스 그대로 | 순수성을 lint가 보장하지 않고, 백테스트가 Nest 컨테이너를 띄워야 해요 |
| C. `src/common/`에 둠 | 하네스 그대로, Nest 없이 import 가능 | common은 "feature를 모르는 코드"인데 규칙은 도메인 핵심이라 자리가 맞지 않아요 |

### Q-019

**봇이 주문 정정(`/orders/{orderId}/modify`)을 쓰나?**

> **실제 확인 (2026-10-30)**: 정정하면 **새 `orderId`**가 생기고, 새 주문은 `PENDING_REPLACE`로 먼저 나타나며 원주문은 `REPLACED`로 끝나요. 봇이 정정을 썼다면 자기 주문을 모르는 주문으로 봤을 거예요. 아래 결정(정정 안 씀)이 맞았어요 → [연동 문서 남은 확인](../integrations/toss-securities-api.md#남은-확인-실제-호출로)
정정 응답의 `orderId`가 원주문과 같은지 새 값인지 공식 문서만으로는 알 수 없어요. 새 값이면 AccountSync가 그 주문을 모르는 주문으로 보고 직접 거래로 잘못 분류할 수 있어요. 정정 결과는 `REPLACED`·`REPLACE_REJECTED` 같은 별도 상태와 레코드로도 와서 추적이 복잡해져요.

> **결정 (2026-10-28)**: A. 봇은 정정을 쓰지 않아요. 가격·수량을 바꾸려면 취소를 확인한 뒤 새 판단으로 새 주문을 내요 → [연동 문서 주문 규칙](../integrations/toss-securities-api.md#주문-규칙), [데이터 모델](../architecture/data-model.md#broker_orders)

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| **A. 정정 안 씀, 취소 후 새 주문** | 판단·주문 1:1 유지, 추적 단순 | 취소 확인까지 한 번 더 기다려요. 체결 우선순위(시간)를 잃어요 |
| B. 정정 사용 | 빠르고 시간 우선순위 유지 | `orderId` 동작을 실제 호출로 먼저 확인해야 하고, 정정 이력 컬럼이 늘어요 |

### Q-018

**사용자용 모의 운영(가상 투자금, 4주 후 실전 전환)이 꼭 필요한가?**
가상 투자금과 실제 돈이 섞여 보이고 전환 시점을 알아보기 어려워요. 규칙 값을 바꿀 때마다 4주를 다시 쌓아야 해서, 값을 조정하는 핵심 시나리오도 막혀요. 모의 성과는 실전보다 좋게 나오는 편이라 어차피 소액 실전에서 다시 확인해야 했어요.

> **결정 (2026-10-27)**: B. 사용자용 모의 모드 제거, 소액 상한 검증 구간으로 대체 → [POL-RISK-09, 13](../policy/risk-management.md#9-검증-구간과-상한-해제-pol-risk-13), [POL-FUND-11, 12](../policy/fund-allocation.md#검증-구간-봇), [ADR-0005](../architecture/adr/0005-in-house-paper-broker.md). Q-008, Q-015를 대체해요

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| A. 모의 유지, 기간만 10거래일로 단축 | 전략 검증에 돈이 들지 않음 | 가상·실제 투자금 혼동, 전환 단계가 그대로 남음 |
| **B. 모의 제거. 새 봇은 실제 계좌로 시작하되 상한(예: 10만 원)을 걸고, 기준(10거래일·30건·순손익·손익비·MDD)을 넘으면 상한 해제** | 화면에 실제 돈만 있음. 사용자가 알아야 할 시점은 상한 해제 하나 | 검증에 실제 돈이 듦 (상한과 손실 한도로 제한) |
| C. 모의 제거, 상한도 없음 | 가장 단순 | 엔진 버그나 나쁜 규칙이 큰 돈으로 바로 이어짐 |

- 엔진 버그(주문 반복 등)는 사용자 기능이 아니라 개발 단계에서 PaperBroker로 잡아요 ([로드맵 M3](./roadmap.md#마일스톤))
- 판단이 바뀌는 변경만 검증 구간을 다시 시작하고, 위험만 줄이는 변경은 기록을 이어 써요

### Q-017

**장전 점검(08:30)에서 보는 공시·뉴스·해외 증시·예상 체결가는 어디서 가져오나?**

> **결정 (2026-10-26)**: 네 항목 모두 A (권장 조합) → [재평가 정책 POL-REEV-06, 07](../policy/position-reevaluation.md#장전-점검과-개장-직후-점검-pol-reev-06), [ADR-0008](../architecture/adr/0008-external-data-numeric-only.md), [DART 연동](../integrations/dart-open-api.md)
[재평가 정책](../policy/position-reevaluation.md)의 장전 점검은 이 네 가지를 보고 시초가 대응(갭 상승 시 매도 시각, 갭 하락 시 손절 여부)을 정해요. 그런데 토스 API로는 일부만 얻을 수 있어요(2026-10-26 확인).

| 항목 | 토스 API | 확인 내용 |
| --- | --- | --- |
| 공시 | 없음 | |
| 뉴스 | 없음 | |
| 해외 증시 | 일부 | 시장 지표는 국내 지수·국채 8종(`KOSPI`, `KOSDAQ`, `KR_BOND_*`)뿐. 미국 개별 종목·ETF 시세와 원/달러 환율은 있음 |
| 예상 체결가 | 없음 | 현재가·호가 응답에 예상 체결가 필드가 없음. 국내 시세는 KRX+NXT 통합이라 NXT 프리마켓(08:00~) 체결이 현재가에 반영될 가능성이 있음 (실제 호출로 확인 필요) |

모든 선택지에 공통으로 적용하는 원칙: 외부 데이터도 **숫자나 정해진 코드로 바꿀 수 있는 것만** 판단 조건에 써요. 근거 카드에 "공시 유형 B(주요사항보고) 있음"처럼 기록할 수 있어야 해요 ([F3 표현 원칙](../product/features/f3-rationale-report.md#개요)).

**1. 공시**

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| **A. 금융감독원 [DART Open API](https://opendart.fss.or.kr/guide/detail.do?apiGrpCd=DS001&apiId=2019001) 공시검색 (권장)** | 공식 무료 API. 응답에 종목코드·공시 유형 코드(정기·주요사항·거래소공시 등)·접수일이 있어 숫자 조건으로 쓰기 쉬움. 일일 약 2만 건 한도로 충분 | API 키를 하나 더 관리해야 함. 공시 내용(호재·악재)은 해석하지 않음 |
| B. 사용 안 함 | 구현 없음 | 밤사이 악재 공시가 있어도 모르고 시초가를 맞음 |
| C. 웹 검색·스크래핑 | 범위가 넓음 | 사이트 구조 변경에 약하고, 약관 문제 소지, 숫자 근거로 쓰기 어려움 |

권장안 A의 사용 방식: 장전 점검 때 보유 종목의 전 거래일 장 마감 이후 공시를 조회해, **주요사항보고·거래소공시가 있으면 보수적으로 판단**해요(예: 갭 상승이어도 매도 시각을 앞당기고, 해당 종목 신규 진입 금지). 공시 내용을 읽고 판단하지는 않아요.

**2. 뉴스**

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| **A. 판단 조건에 쓰지 않음 (권장)** | 숫자 근거 원칙 유지, 출처 신뢰도 문제 없음. 중요한 사건은 대부분 공시(1번)와 가격(4번)에 드러남 | 공시 없는 이슈(업황 뉴스 등)는 놓침 |
| B. 뉴스 검색 API로 종목명 기사 수를 숫자 지표로 사용 (예: 평소 대비 기사 수 급증) | 숫자로 기록 가능 | 기사 수와 방향(호재·악재)이 무관해 판단 근거로 약함. 동명 기업·중복 기사 처리 필요 |
| C. LLM 웹 검색으로 요약해 판단 | 맥락 이해 | 근거를 숫자로 채점할 수 없고 결과가 매번 달라 검증 불가. 원본 기획 원칙과 충돌 |

뉴스는 나중에 백로그의 "AI 해설"에서 근거 카드 옆 참고 정보로만 보여주는 것을 검토해요.

**3. 해외 증시**

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| **A. 토스 API의 미국 시세로 대표 ETF(예: SPY, QQQ, SOXX) 전일 정규장 등락률 + 원/달러 환율 사용 (권장)** | 이미 쓰는 API라 키·연동 추가 없음. 숫자로 바로 조건화 가능 (예: QQQ −2% 이하면 보수적) | 지수 자체가 아니라 ETF 대용. 토스 미국 시세는 일부 거래소 기준이지만 일봉 종가는 정규장 공식 종가라 등락률 용도로 충분 |
| B. 별도 지수 데이터 소스 연동 | 지수 원값 사용 | 데이터 소스·키 추가, 약관 확인 필요 |
| C. 사용 안 함 | 구현 없음 | 미국장 급락 다음 날의 갭 위험을 반영 못 함 |

**4. 예상 체결가**

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| **A. 대체 지표 + 개장 직후 점검 (권장)** | 추측 없이 실제 체결된 가격으로 판단 | 08:30에 결론을 다 못 내고, 시초가 대응 일부가 09:00 이후로 밀림 |
| B. 동시호가 중 호가 데이터로 예상 체결가를 직접 계산 | 08:30~09:00에 미리 판단 | 토스 문서에 동시호가 중 호가 의미가 설명돼 있지 않아 근거가 약함. 계산 로직이 틀려도 알기 어려움 |
| C. 사용 안 함 | 구현 없음 | 갭 대응이 손절 조건주문에만 의존 |

권장안 A의 사용 방식:
- NXT 거래 종목(`nxtSupported=true`)은 08:00부터 프리마켓 체결가가 통합 현재가에 들어오는지 M0에서 확인하고, 들어오면 그 가격을 갭 추정치로 써요
- NXT 미거래 종목은 09:00 시가 단일가가 체결된 뒤 **개장 직후 점검(09:00~09:05)** 에서 실제 시초가로 판단해요
- 이를 위해 장전 점검을 "08:30 장전 점검(공시·해외 증시·NXT 가격)"과 "09:00 개장 직후 점검(시초가)" 두 단계로 나눠요

**권장 조합 요약**: 공시는 DART, 뉴스는 판단에서 제외, 해외 증시는 토스 미국 ETF 시세와 환율, 예상 체결가는 NXT 프리마켓 가격과 개장 직후 점검으로 대체.

참고: DART의 거래소공시에는 관리종목 지정 공시도 포함될 수 있어요. 확인되면 [Q-012](#q-012)의 관리종목 수집(백로그 9-1)도 같은 연동으로 해결할 수 있어요.

Q-012~Q-014는 공식 문서를 확인하면서 새로 생긴 질문이에요.

### Q-014

**같은 종목을 여러 봇이나 직접 거래가 동시에 다루면?**
국내 주식은 같은 종목에 반대 방향 미체결 주문이 있으면 새 주문이 `409 opposite-pending-order-exists`로 거부돼요. 예) 봇 A의 매수 주문이 미체결인데 봇 B가 같은 종목을 매도하면 거부돼요. 또 조건주문 OCO는 종목당 1개만 걸 수 있어요.

> **결정 (2026-10-26)**: A. 종목 잠금 → [POL-RISK-16](../policy/risk-management.md#5-1-종목-잠금-pol-risk-16)

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| **A. 종목 잠금: 한 종목은 한 시점에 한 봇만 보유·주문. 직접 거래 미체결 주문이 있는 종목에는 봇이 진입하지 않음 (권장)** | 409와 수량 다툼이 구조적으로 사라짐. 포지션 귀속이 명확함 | 인기 종목을 두 봇이 동시에 못 삼 |
| B. 공유 허용, 종목별로 주문을 줄 세우고 반대 방향 미체결을 취소 후 주문 | 기회 손실 없음 | 다른 봇의 주문을 취소하는 부작용, 구현 복잡 |

어느 쪽이든 409를 받으면 재시도하지 않고 "건너뛴 판단"으로 기록해요.

### Q-016

**정액 봇과 정률 봇이 같은 시각에 시작하거나, 돈이 설정 금액보다 모자라면 어떻게 배분하나?**
예) 운용 자산 100만 원, 정액 봇 A 30만 원, 정률 봇 B 50%. 정액 1만 원 봇인데 9천 원만 남은 경우.

> **결정 (2026-10-26)**: 세 항목 모두 A → [POL-FUND-03, 13~16](../policy/fund-allocation.md#정액정률-혼합), [실전 예시](../policy/fund-allocation.md#실전-예시)

| 항목 | 선택지 | 결과 |
| --- | --- | --- |
| 정률 기준 | **A. 운용 자산 전체 기준** / B. 정액을 뺀 나머지 기준 | A: B봇 50만 원. B였다면 35만 원 |
| 부족 시 처리 | **A. 시작 보류 + 알림** / B. 최소 금액 이상이면 줄여서 시작 / C. 남은 금액으로 줄여서 시작 | 정액은 설정한 그 금액이라는 뜻을 지킴 |
| 확정 순서 | **A. 정률 먼저, 정액은 남은 돈에서 시작 우선순위 순** / B. 정액 먼저 / C. 봇마다 정한 순서 | 정률 합 ≤ 100%라 정률 봇은 항상 시작, 부족은 정액 봇에서만 생김 |

함께 정한 세부: 보류된 정액 봇 뒤 순서의 정액 봇도 남은 금액 안에 들어가면 확정해요. 1회 주문 금액보다 작은 투자금이면 정률·정액 관계없이 보류해요(POL-FUND-16).

# ADR-0003. 판단 기록을 먼저 저장하고, 그 id를 clientOrderId로 주문

- 상태: 제안
- 날짜: 2026-10-26

## 맥락

성공 기준은 "모든 주문에 근거 로그 100%"예요([G1](../../product/prd.md#2-목표와-비목표)). 또 네트워크 오류로 주문을 재시도할 때 중복 주문이 나면 안 돼요. 토스 API는 주문 중복 방지 ID(`clientOrderId`)를 제공해요.

## 결정

1. 주문 전에 `decisions` 행(근거·점수·예측)을 저장해요. 저장이 실패하면 주문하지 않아요
2. `decisions.id`는 UUID(36자)로 만들고 그대로 `clientOrderId`로 써요. 토스 제약(최대 36자, 영숫자·`-`·`_`)에 맞아요
3. 재시도는 같은 `clientOrderId`로만 해요. 토스의 중복 방지는 **10분만 유효**하므로, 10분이 지난 재시도는 먼저 주문 조회로 접수 여부를 확인해요
4. 주문 응답의 `orderId`를 `order`에 저장해요. 토스의 주문 조회 응답에는 `clientOrderId`가 없어서, AccountSync는 이 `orderId`로 봇 주문과 직접 거래를 구분해요 (FR-MAN-01)

## 결과

- 근거 없는 봇 주문이 구조적으로 생길 수 없어요
- 재시도가 안전해지고, 주문 → 근거 추적이 `order.decision_id` 하나로 끝나요
- 감수: 주문 요청은 성공했는데 응답을 못 받으면 `orderId`가 비어요. 같은 `clientOrderId`로 재요청해 첫 결과(`orderId`)를 받아 채워요
- 감수: 주문 직전 DB 쓰기 1회만큼 지연이 늘어요. 스캘핑에서 문제 되면 측정 후 재검토해요

## 검토한 대안

- 주문 후 기록: 주문은 됐는데 기록이 실패하는 경우가 생겨요
- 별도 UUID를 clientOrderId로 쓰고 매핑 테이블 유지: 키가 둘이 돼 추적이 복잡해요
